# FitWise 팀 개발 순서

## 0. 공통 기반을 먼저 공유

현재 상태는 Streamlit + SQLite로 실행 가능한 baseline입니다. 실제 AI API 호출은 아직 없습니다.
이번 작업은 파일 생성 및 로컬 검증까지이며, 커밋·push·PR·실제 feature 브랜치 생성은 하지 않습니다.

1. 팀장이 현재 기반의 동작을 확인하고 공통 기반 커밋을 `main`에 반영합니다.
2. 전원이 Python 3.12, `requirements.txt`, `.env.example`로 같은 환경을 준비합니다.
3. `docs/CONTRACTS.md`의 DB·함수 반환값·측정 기준을 함께 확인합니다.
4. 이 기반 커밋을 포함한 `main`에서 각 feature 브랜치를 생성합니다.
5. 담당자는 자신의 파일을 중심으로 작은 PR을 올립니다. 공통 파일 변경은 담당자와 먼저 규격을 맞춥니다.

```powershell
git switch main
git pull --ff-only origin main
git switch -c feature/review-agent
# 다른 담당자는 마지막 줄을 자신의 브랜치 이름으로 변경
```

## 1. 담당 범위

| 브랜치 | 주요 담당 파일 | 데이터 | 공통 파일 협의 대상 |
|---|---|---|---|
| `feature/review-agent` | `app/review_agent/`, `views/products.py`, 리뷰 UI | products, reviews | `views/product_detail.py`의 리뷰 구간, `app/ui.py` |
| `feature/fit-agent` | `app/fit_agent/`, `views/fit_result.py` | users, orders, returns | `app/db.py`, `app/schema.sql`, `app/repository.py` |
| `feature/admin-dashboard` | `app/monitoring/`, `views/admin_dashboard.py`, 상품 상세 기본 UI | agent_logs, resource_logs | `views/product_detail.py`의 상품·실측·선택 구간 |

`streamlit_app.py`, `app/services.py`, `app/config.py`, `requirements.txt`는 공통 통합 파일입니다.
리뷰 담당은 리뷰 컴포넌트를 `app/review_agent/` 아래 별도 UI 파일로 분리하고,
상세 담당은 그 함수를 호출하는 방식으로 겹치는 파일 수정을 줄이세요.

## 2. Review 담당: feature/review-agent

다음 순서로 진행합니다.

1. **데이터 정리:** 상품/리뷰 입력 규칙, 중복·빈 리뷰·평점 범위, 사이즈 정규화를 확정합니다.
2. **목록 완성:** 카테고리·서브카테고리·검색·정렬, 상품 이미지와 리뷰 수 표시를 개발합니다.
3. **분석 평가 자료:** 정사이즈/큼/작음, 소매·허리·기장, 부정 표현과 혼합 의견을 포함한 테스트 리뷰와 정답 표본을 준비합니다.
4. **규칙 분석 개선:** 긍정·중립·부정, 사이즈·핏 키워드, 중복 집계 기준을 개선합니다. 반환 필드는 유지합니다.
5. **API 연결:** 팀이 정한 모델을 `.env`의 `OPENAI_MODEL`로 읽고, `OPENAI_API_KEY`를 서버 측에서만 사용합니다. 클라이언트 코드는 새 `app/llm/`에 분리합니다. SDK 버전 추가는 공통 PR로 공유합니다.
6. **실패 처리:** 키 없음·타임아웃·요청 제한·잘못된 JSON·빈 응답을 처리합니다. baseline 전환 여부와 실제 분석 모드를 UI와 로그에 분명히 남깁니다.
7. **출력 검증:** 모델이 숫자를 임의 생성하지 않도록 평점 비율은 Python으로 계산합니다. 구조화된 모델 출력은 계약에 맞게 검증하며 리뷰 문장을 실행 지시로 취급하지 않습니다.
8. **리뷰 화면 연결:** 실행 버튼·로딩·오류·요약·근거 원문을 표시하고 rerun으로 재호출되지 않는지 확인합니다.
9. **PR:** 규칙 테스트, API mock 테스트, 리뷰 없는 상품 테스트를 포함합니다. Fit 담당이 반환값을 소비하는 통합 테스트를 통과시킵니다.

완료 기준: 키 없이 baseline 실행, 키가 있는 명시적 API 모드에서 모델 분석, 실패 시 상태 설명, 숫자·근거 일치.

## 3. Fit 담당: feature/fit-agent

1. **DB 규칙 확정:** 반품 기간 종료 여부, 주문 취소/교환 제외, 주문 한 건의 단위, 중복 반품 방지를 확정합니다. 스키마 변경은 마이그레이션과 함께 별도 PR로 공유합니다.
   작업 도중 생성된 `data/fashion_shop.db`는 user_id/product_id 및 product_sizes 테이블을 사용하는 별도 스키마입니다. 현재 앱의 `data/demo/fashion_shop.db`와 어느 규격을 채택할지 먼저 결정하고, 원본 백업 후 변환 스크립트로 통합하세요. 현재 기반은 원본을 삭제하거나 덮어쓰지 않습니다.
2. **집계 함수 분리:** 개인 전체/동일 카테고리/사이즈 이력, 상품 전체/사이즈 반품률을 테스트 가능한 함수로 분리합니다.
3. **결측 처리:** 신규 사용자·신규 상품·선택 사이즈 이력 없음·리뷰 없음·반품 0건/전부 반품을 먼저 검증합니다.
4. **점수 정책:** 현재 20/30/15/20/15 가중치를 근거와 함께 검토하고, 최소 표본·평활화·브랜드별 사이즈 차이 정책을 합의합니다.
5. **Review 통합:** `positive_pct`, `count`, `negative_keywords`를 계약대로 소비하고, API 분석 문구와 계산된 수치를 분리합니다.
6. **근거 설명:** 분모/분자·적용 가중치·누락 항목·주의점을 표시합니다. 모델을 사용하더라도 점수 계산은 검증 가능한 Python 로직으로 유지합니다.
7. **결과 화면:** 사용자/상품/사이즈가 일치하는지 확인하고, 사이즈 비교·구매 이력 요약을 추가합니다. 추천 사이즈는 실측/표본 정책 확정 후 구현합니다.
8. **PR:** 손으로 계산한 고정 사례, 데이터 누락, 0~100 범위, 잘못된 ID/사이즈를 검증합니다.

완료 기준: 동일 입력·데이터에 동일 점수, 표본 없는 항목을 성공률 100%로 오인하지 않음, 반품 확률로 표현하지 않음.

## 4. Admin 담당: feature/admin-dashboard

1. **측정 정의 확정:** 프로세스 CPU·RSS·처리시간·서비스 응답시간의 구간과 단위를 유지합니다. 브라우저 체감 응답시간이 필요하면 별도 지표로 정의합니다.
2. **계측 검증:** 일반 조회 1개, Review 1개, Fit 내부 Review+Fit의 로그 수·request_id·오류 기록을 검증합니다.
3. **상품 상세 완성:** 가격·리뷰 개수·사이즈 실측·선택 UI를 정리하고 Review 담당의 컴포넌트를 붙입니다.
4. **Dashboard 확장:** 기간·작업·성공 여부 필터, 중앙값/p95·표본 수·최근 로그를 추가합니다. 실패를 성공 평균에 섞지 않습니다.
5. **비교 실험:** 동일 상품·사이즈로 워밍업 후 각 작업을 같은 횟수 반복합니다. 한 세션에서 실행하고 warm/cold 구간을 분리합니다.
6. **API 모드 비교:** 원격 모델 처리 대기시간과 로컬 CPU 비용을 구분합니다. API 사용량/비용이 필요하면 별도 컬럼과 정책으로 추가합니다.
7. **운영 준비:** 로그 보관 기간·DB 인덱스·쓰기 실패 처리·관리자 인증을 구현합니다. 다중 사용자 배포 전 CPU 측정의 프로세스 간섭을 검토합니다.
8. **PR:** 정상/실패 로그, 빈 Dashboard, 같은 요청의 중복 집계 방지, 반복 실행 비교 결과를 제출합니다.

완료 기준: 표시값이 DB 실측과 일치하고, Fit의 내부 Review 시간이 중복 합산되지 않으며 실패 로그를 추적 가능.

## 5. 전체 진행 및 병합 순서

1. **공통 기반 main 반영** → DB와 함수 규격 동결.
2. **세 브랜치 개발 시작** → Review·Fit 분석과 Admin 계측은 현재 baseline 규격을 사용해 병렬 개발 가능.
3. **공통 스키마/환경 변경 PR 우선 병합** → 각 담당자는 최신 main을 자신의 브랜치에 merge.
4. **Review PR 병합** → Fit 담당이 실제 Review 출력으로 통합 검증.
5. **Fit PR 병합** → Admin 담당이 전체 파이프라인 실측과 로그 연결 검증.
6. **Admin·상품 상세 통합 PR 병합** → UI 흐름 및 비교 차트 최종 확인.
7. **공동 검증** → 상품 선택 → 리뷰 분석 → 사용자/사이즈 선택 → 적합도 → Dashboard → 재실행/실패 확인.

브랜치 간 규격을 변경하지 않았다면 독립적인 UI PR은 앞서 병합해도 됩니다.
완료된 브랜치만 PR로 main에 병합하며, main에서 직접 기능 개발하지 않습니다.

```powershell
git add <담당 파일>
git commit -m "feat: 구현한 기능 요약"
git push -u origin feature/review-agent
# GitHub에서 base=main, compare=본인 feature 브랜치로 PR 작성
```

## 6. PR 공통 체크리스트

- [ ] `python -m unittest discover -s tests -v` 통과.
- [ ] 새 환경에서 requirements 설치 후 Streamlit 실행 가능.
- [ ] .env, API 키, 개인 DB가 diff에 포함되지 않음.
- [ ] 변경한 계약/스키마/점수 정책과 검증 결과를 PR에 설명.
- [ ] 빈 데이터와 실패 상태를 UI에서 확인.
- [ ] 일반 rerun이 유료 API를 자동 재호출하지 않음.
- [ ] 인증 없는 현재 로컬 데모와 배포 버전의 차이를 구분.
